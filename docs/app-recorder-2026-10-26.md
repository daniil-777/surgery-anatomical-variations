# Recording across the generation lab

The existing Viscera VideoRecorder and VideoRecorderPanel now also build a portable app recorder. Every lab entry page exposes **Record app**; Viscera retains **Scene video** for native scene-only capture. The app recorder opens a separate window: choose the lab tab in the browser's sharing picker to follow navigation in that tab, or choose a browser window/screen to include other tabs. Microphone narration is selected by default and can be switched off before Start. No capture permission is requested merely by opening the controls.

The original recorder owns encoding, microphone selection, mute, pause, safe stop, 10-minute/256-MB limits, preview and download. Files stay in memory on this device; there is no upload. Keep the controller window open and download the completed video before closing it. Sharing another origin does not grant that origin access to the recording; use the controller window if its inline controls cannot follow you across origins.

Full-app capture has a new `native-display` path. It passes the browser's video track directly to MediaRecorder, preserving audio track membership. It avoids the animation-frame compositor that can stop painting when a controller is in the background. Quality options bound the capture size; the report records the actual negotiated dimensions and does not claim an encoded frame rate. Existing native scene rendering and the fixed-size compositor remain unchanged. A same-origin Web Lock prevents independent tabs from opening competing app recorders; BroadcastChannel carries only status and pause/mute/stop commands, never media or login data. The capture source is always chosen by the user.

Source/build: `apps/studio/src/recording/app/` and `scripts/build_app_recorder.mjs`. Run the build script after changing the recorder, and commit `apps/studio/public/recorder/`. CI runs `--check` to catch stale generated assets. Copy that folder unchanged to the parent lab's `recorder/`; its build verifies the manifest SHA-256 values and inserts launchers into its existing anatomy HTML without replacing anatomy models. The parent lab has a nine-entry browser release gate.

The private login integration uses `/auth/recorder/launcher.js` and the narrowly allowlisted `services.web.recording_assets.recording_asset` response. Its recorder page permits `media-src blob:` for local preview. Login credentials, sessions, private bundles, and model files are not made public. The separate login work remains in the private workspace and is installed on the Mac’s loopback-only private studio, using the existing access configuration; `app-recorder-private-login.patch` contains just the recorder integration for that server.

Validation on Chrome/macOS: 110 unit checks covering the recording engine and native scene leases; all nine entry pages open the app recorder; a real H.264/AAC export follows iframe changes and full navigation with the recording window in the background; synthetic audio verifies narration and mute; pause/resume, cancelled sharing, blocked popups, duplicate controllers, download and playback; keyboard/layout checks and zero axe WCAG A/AA violations in the recorder dialog at 375, 768 and 1440 px; protected-login recording continues through sign-in; 38 existing access-boundary checks and two allowlist checks. The original recorder's video-only and Opus export checks pass; its selected-microphone AAC/mute test passed when run alone after a timing failure during concurrent GPU recording tests. No physical microphone was used for automated testing.

Browser sharing is available only where getDisplayMedia is supported; the panel explains unsupported environments. Native tab/window selection and microphone permissions remain required. No guarantee is made about capture of a minimized/occluded application: this is controlled by the browser/OS.

References: [W3C Screen Capture](https://www.w3.org/TR/screen-capture/) specifies explicit source selection, transient activation, picker hints, permissions policy and inaccessible sources. [Chrome background tabs](https://developer.chrome.com/blog/background_tabs) explains background animation throttling; this motivates avoiding a canvas-copy loop in the controller.

The full 2D/3D portal is installed behind the same existing login at `http://127.0.0.1:5181/`; Viscera's private studio remains at `http://127.0.0.1:5180/`. Run the private workspace installer with `--application generation-lab --build <tested portal build>` for that portal. No GitHub Pages site was enabled for the private parent repository. Its CI builds/tests and skips public deployment until hosting is explicitly configured. The protected portal passed another ten browser cases, including decoded narrated capture, signed-in navigation and successful 2D/3D/architecture generation. All 1,577 installed portal files were verified against the tested build.
